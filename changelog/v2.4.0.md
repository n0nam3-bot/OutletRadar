# Outlet Radar v2.4.0 — Nike.com source and Channel3 cross-store comparison

## Nike.com in the main catalog (API.SH)
- Nike and Jordan searches (and "All brands" searches that name a Nike model such as Dunk, Air Max or Air Force) now also query API.SH, so Nike.com listings appear in the catalog and are grouped with StockX, GOAT and other listings of the same product by style code. Cost: 1 API.SH request per uncached search, within the existing 25/day and 1,000/month ceilings.
- It follows the same rules as every other source: shared snapshot (12 h), budget protection, circuit breaker, stale fallback, and never-empty behavior. Nike offers are saved to the normalized catalog.
- Searches for other brands do not call API.SH.

## Channel3 live comparison (adidas, New Balance, Puma, Reebok, Vans and many stores)
- Most brands publish no public product API. Channel3 is a product-data API that matches one product to offers at many merchants and brand sites. It is added to **Compare offers**: opening a product's comparison now makes one Channel3 search and adds offers from other stores (for example Foot Locker, JD Sports, Champs, Snipes, adidas.com, newbalance.com) that match the exact product. Matching requires every model word and the same model numbers, so a different colorway or model is excluded.
- Free plan: 1,000 credits per month, one credit per search. App ceilings: 30/day and 900/month (`CHANNEL3_DAILY_BUDGET`, `CHANNEL3_MONTHLY_BUDGET`).
- Channel3 asks integrators not to keep prices, availability or offer links for more than a few hours, so its offers are cached for 3 hours, are never written to the catalog tables, and an incomplete Channel3 answer is not cached.
- Optional: without `CHANNEL3_API_KEY` Compare behaves as before.

## Coverage fill-in
- When a search is answered from the shared catalog and a configured source (including Nike.com) has no fresh snapshot for it, the search is quietly queued (`reason: coverage`). The daily warm-up job then runs a full discovery for the most requested ones, adding retailers that an older stored result was missing. Visitors see no notice for this.

## Other
- The "not configured" re-check now tests each source's own key (it previously assumed PCKT for every non-Shopping source).
- Admin provider labels and `/api/health` include Nike (API.SH) and Channel3.
- Retailer coverage report: Nike is attributed to API.SH. Offers that arrive only through Channel3 are not saved, so they appear in Compare but not in that report.

## Migration and configuration
- No database migration.
- Optional new variables: `CHANNEL3_API_KEY`, `CHANNEL3_DAILY_BUDGET`, `CHANNEL3_MONTHLY_BUDGET`. `API_SH_KEY` (already used by the legacy Nike features) now also enables the Nike.com source.

## Validation
- Production build and TypeScript check pass.
- 49 scenario checks pass against PostgreSQL with mocked providers, including: Nike queried only for Nike-family searches; Nike listing grouped with marketplace listings and persisted; Nike budget exhaustion degrading gracefully; coverage queueing; Channel3 returning Foot Locker, Champs and Snipes while excluding a different colorway and a different model; one offer kept per retailer; out-of-stock signal preserved; 3-hour cache; no catalog persistence; exhausted budget leaving catalog offers visible.
- Not exercised against live API.SH, Channel3, PCKT, SerpApi or Neon. The Channel3 response parser is defensive because its documentation shows more than one response form; verify with one real Compare after adding the key.
