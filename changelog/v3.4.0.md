# Outlet Radar v3.4.0 — Built for many visitors: edge caching, demand counting, demand-driven refresh

## Goal
Let hundreds of visitors run many searches without each search costing provider credits or database time, and without ever blocking anyone. Reads become cheap and unlimited; the scarce resource, fresh data, is spent on what people actually search for.

## What changed
- **Edge caching of search results.** `GET /api/catalog` now sends cache headers, so the CDN serves a complete answer for 10 minutes (then serves it stale while refreshing in the background). When 100 visitors search "air jordan 4", the first reaches the server and database; the rest are answered at the edge. Incomplete answers (a provider was out of budget, only saved data was shown) are cached for 30 seconds only, and errors are never cached. `CATALOG_CDN_SECONDS` changes the lifetime (0 turns it off).
- **One URL per search.** The page now sends the search words in a normalized form (shorthand expanded, lowercase), so "AJ1", "aj 1" and "Air Jordan 1" share one cached response.
- **Anonymous search demand.** Because a cached search may never reach the server, the browser reports each search to `POST /api/search-log`. Only the filters and the lowercase search words are stored, as a daily counter (`search_demand_daily`): no IP address, cookie or user agent. Text that looks like an e-mail address or phone number is ignored, at most 5,000 new rows are created per day, and rows older than 60 days are deleted.
- **Demand-driven refresh.** The daily warm-up now refreshes, in this order: searches that visitors could only be served partially (the queue), then the most-searched filters of the last 7 days whose cached answer has expired (searched at least `WARM_MIN_SEARCHES` times, default 2), then the static seed list. Free-tier credits go to what people actually look for.
- **Admin "Search demand" section** on `/admin/providers`: the most-searched filters over 7 days and the searches that found nothing, which is the list of what to load next.
- New guide, `docs/scaling.md`: what limits apply at hundreds of visitors, what this release does about them, and what cannot be free.

## Not changed (honest limits)
- **Compare offers** is still a per-click server request (it is a POST), and the saved-catalog lookup is a table scan. Both are fine for tens of thousands of products and hundreds of visitors, because the CDN and the exact-query cache absorb repeated searches. A search index and an edge read layer are the next steps if the catalog or traffic grows a lot.
- Per-size resale asks for thousands of products still have no free bulk source; the warm-up covers the most-searched products first.
- Vercel's Hobby plan is for non-commercial use. Once the site earns affiliate income, the Pro plan is required.

## Migration and configuration
- Run `db/migrations/007_search_demand_daily.sql` in Neon (additive, repeatable). Without it, searches work normally and demand is simply not recorded.
- Optional variables: `CATALOG_CDN_SECONDS`, `WARM_MIN_SEARCHES`.

## Validation
- Production build and TypeScript check pass.
- 15 new checks (133 total in the pipeline suite) for: cacheable complete answers, 30-second incomplete answers, no caching of errors, configurable lifetime, one shared row for equivalent searches, rejection of invalid / e-mail-like / phone-like input, the daily row cap, the admin report, demand-ordered warm-up, the minimum-search threshold, and pruning.
- Whether the CDN actually serves cached responses is a property of Vercel's network and was not tested here. Verify after deploying: request the same search twice and look for the `x-vercel-cache: HIT` response header.
